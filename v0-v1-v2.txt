------------------------------------------------------------------------
V0 — PROTOTYPE (7/7)
------------------------------------------------------------------------

1. Authentication
   - bcrypt, with lazy migration of old SHA-256 hashes on next login.
   - HMAC access token lasting 60 minutes; hashed, revocable refresh token
     lasting 14 days. The frontend refreshes silently.
   - Every resource carries an ownership check in the API, because it holds
     a Supabase service credential. RLS could be added as a second layer.
   - The token travels in the Authorization header, not a cookie: frontend
     and backend are separate Render domains.

2. Submit and observe
   - POST /leads/process validates, checks the daily cap, inserts a jobs
     row and returns 202 + job_id. It never waits for a model.
   - GET /jobs/{id} reports status, per-agent progress and results.

3. Durable job queue
   - jobs moves pending -> running -> done | failed. The claim boundary is
     a conditional UPDATE, so exactly one process can own a row.
   - Credentials in a job are wiped when it finishes. A user's saved keys are
     Fernet-encrypted in users and re-encrypted before they're queued; the
     worker decrypts them when the job starts.
   - Load test (2026-09-03): 20/20 jobs completed, 0 failed, 0 stuck, with 12
     contested claims correctly rejected.

4. One worker
   - backend/worker.py claims jobs, runs the graph once per lead, writes
     results.
   - RUN_WORKER_IN_PROCESS=1 runs it as a thread inside the API process —
     how local dev and the single-service deploy both run.
   - MAX_CONCURRENT_JOBS=10, with worker.main sizing the executor to match.
     Without that, asyncio.to_thread's default pool caps at 5 on a 1-vCPU
     box and the setting is unreachable.

5. Hot store (company-research cache)
   - Supabase rows keyed by normalized company name + ICP hash, so two
     different ICPs never share a fit score. TTL 7 days; force_refresh
     bypasses it.
   - A unique-key sentinel lets one miss do the research while concurrent
     misses wait, instead of paying for the same search twice.
   - A repeat-company lead skips the company node: about a third of the
     tokens, 55s uncached -> 31s average cached (same lead, 10 runs).

6. Polling
   - waitForJob in frontend/src/App.jsx polls GET /jobs/{id} every
     JOB_POLL_MS = 5000.
   - Progress is per agent and includes Cached and Skipped stages, so a
     cache hit and a below-threshold email both show a reason.

7. Pydantic bounds
   - Model output is parsed into CompanyResearchResult and
     LeadScoringResult; a parse failure is a permanent error, not a retry.
   - Request models bound their inputs: username 3-50, password 8-128,
     company_context <= 4000, bulk import <= MAX_BULK_IMPORT, smtp_port
     1-65535, list limit 1-500.

V1 — REAL USERS (8/8)
------------------------------------------------------------------------

1. Idempotency
   - POST /leads/process takes an optional Idempotency-Key header. A repeat
     with the same key returns the existing job with 200 plus
     idempotent_replay: true instead of enqueuing and billing twice.
   - Backed by jobs.idempotency_key with a partial unique index, which also
     settles two concurrent submissions to one row.
   - If the column is missing the endpoint degrades to no idempotency
     rather than failing every request.

2. Durable sessions and storage
   - Supabase carries jobs, the research cache, sessions and the shared
     limits. No Redis and no Celery — the extra round trip is small next to
     a Tavily or Gemini call.
   - Refresh tokens are stored hashed and can be revoked.

3. Wall-clock limits
   - PIPELINE_TIMEOUT_S = 600 per lead, multiplied by the lead count for
     the whole job.
   - Stale recovery ages each job against its own started_at budget
     (timeout x lead count x attempts), so a starting worker never reaps
     another worker's in-flight work.

4. Rate limits
   - DAILY_LEAD_CAP = 5 operator-funded leads per account per UTC day,
     returning 429 before enqueue. A pending/running job reserves credits;
     a failed job refunds them. When both user keys are saved and Gemini is
     selected, the daily cap is lifted; on Cloudflare it still applies.
   - LOGIN_MAX_FAILURES = 5 per account; SIGNUP_MAX_PER_IP = 10 per
     SIGNUP_WINDOW_S = 3600, which slows daily-credit farming.
   - Every 429 carries Retry-After — the daily cap computes seconds to UTC
     midnight rather than guessing.

5. Prompt caching
   - Static prompt content goes before the lead data, because a cached
     prefix ends at the first differing byte.
   - expected_output moved into the system message alongside role, goal and
     backstory. The scoring node's contiguous reusable prefix went from 136
     to 840 characters.

6. Validation
   - Pydantic on the way in (request models) and on the way out (structured
     model output).
   - ICP is required: processing without company context returns 400 and
     the frontend blocks submission. The value is frozen into each job at
     enqueue, so a later edit cannot change work already queued.

7. Graceful shutdown
   - SIGTERM/SIGINT stop the claim loop and wait WORKER_SHUTDOWN_GRACE_S
     (25s) for in-flight jobs.
   - 25s is deliberately below p99 job duration: Render SIGKILLs about 30s
     after SIGTERM, so a larger number would never be honoured. Jobs past
     the window keep running and are reaped on the next boot rather than
     being cancelled after paid model work.
   - Handlers install inside try/except ValueError, because with
     RUN_WORKER_IN_PROCESS=1 the loop is on a non-main thread where
     signal.signal refuses.

8. Logs
   - Structured JSON logs correlating request_id, job_id and lead_id.
   - Langfuse and Grafana receive worker traces and metrics; alerts cover
     job failures and no jobs processed for 30 minutes.
   - Per-node LangGraph usage gives exact per-agent token counts and timing;
     USD cost uses configured rate constants. The old even split survives
     only as a fallback for a stage that reports one total.

V2 — SCALE (6/6)
------------------------------------------------------------------------

1. Model routing — COMPLETE
   - Gemini judgment and retrieval now both use gemini-3-flash-preview.
     Cloudflare still uses its configured Workers AI model. The two model
     slots remain separate in code to allow different choices later.

2. Circuit breaker and fallback — COMPLETE
   - is_retryable classifies on exception text, because no single type
     spans Gemini, Workers AI and langchain's re-wrapping. Transport
     failures retry with full jitter; a parse failure fails immediately
     instead of re-running every model call twice more at full price.
     Unknown failures retry.
   - BREAKER_THRESHOLD consecutive retryable job failures pause claiming
     for BREAKER_COOLDOWN_S; one success resets the streak. Only transport
     failures count, so a run of malformed leads cannot stop the queue
     while a provider outage still does.
   - LLM_FALLBACK_MODEL can rebuild the graph on the other provider for the
     remaining attempts on operator-funded jobs. A job using the user's
     Gemini key never switches to the operator's fallback provider. Fallback
     is off by default: historical measured scores differ across providers
     (96 vs 91, 78 vs 94 on the same leads), so failover trades score
     consistency for availability. That is an operator decision.

3. Per-tenant quotas and fairness — COMPLETE
   - DAILY_LEAD_CAP caps operator-funded accounts before enqueue. With both
     user keys on Gemini, processing is uncapped; Cloudflare still uses the
     operator model key and keeps the cap.
   - claim_next_job scans the oldest FAIR_CLAIM_SCAN_LIMIT pending rows and
     queue_policy.choose_round_robin_job rotates across user_id while
     keeping each user's jobs FIFO.
   - The cursor is process-local because this deployment runs one worker
     process; the conditional UPDATE stays as the cross-process safety net.
   - tests/test_queue_policy.py covers the claim order, no network needed.

4. Tool sandboxing — COMPLETE
   - read_website_content only fetches public addresses. _assert_public_url
     checks the scheme and the resolved IPs, and up to 5 redirects are
     followed by hand so every hop is re-checked — requests' own redirect
     following would skip past the check. Known ceiling: check-then-connect,
     so DNS rebinding is not covered.
   - Scraped pages are fenced as untrusted content, the same treatment lead
     fields get, because a page is far easier for an outsider to control.
   - Tool results are memoized per graph on (job_id, step, args). This came
     out of traces where an agent repeated identical searches and inflated
     one stage to roughly 95,700 tokens.
   - tests/test_pipeline.py rejects 9 hostile URLs, including the
     link-local metadata address.

5. Worker scaling and queue-depth autoscaling — COMPLETE (as slots)
   - The host is single-instance, so there is no worker count to scale. The
     same control loop moves the concurrency slots inside the one worker.
   - pending_depth() counts waiting jobs each poll and publishes it as
     queue_pending_jobs; queue_policy.next_concurrency rides the target
     between WORKER_MIN_CONCURRENCY (2) and MAX_CONCURRENT_JOBS (10) and
     publishes it as worker_target_concurrency.
   - Scale-up is immediate and multiplicative: making already-queued work wait
     out a timer would be strictly worse than the fixed ceiling it replaced.
     Scale-in halves, only after SCALE_COOLDOWN_S, and never cancels a running
     job — those model calls are already paid for.
   - The executor stays sized to MAX_CONCURRENT_JOBS, not the current target,
     so a scale-up starts work at once instead of queueing behind a small pool.
   - Verified live: the drain harness logged "Scaling concurrency 2 -> 4
     (queue depth 6)" and back to 2 when the queue emptied, with 20/20 jobs
     done and drain time 39.4s against 43.3s for the fixed ceiling.
     tests/test_queue_policy.py covers the decision function, no network.
   - Scope: worker-count scaling would still need a multi-instance host. At
     DAILY_LEAD_CAP=5 the target rests at the minimum nearly always — this
     buys an automatic response to a backlog, not extra throughput.

6. Cost and TTFT dashboards — COMPLETE
   - Metrics cover tokens, estimated USD cost, TTFT and tokens/second,
     labelled by the provider that actually served each attempt — which
     matters when fallback switches provider mid-job. The React dashboard
     shows processed leads, average score, total cost, tokens and auto-drafted
     emails, plus monthly cost/token charts with year selectors.
   - The cost estimator still uses the former $0.15/M input and $0.60/M
     output rates; charts aren't actual bills for the newer Gemini model.
   - Gemini streams for TTFT. Workers AI does not: its streaming adapter
     reported 162/126/288 tokens where non-streaming reported 81/60/141, so
     enabling it would have doubled the cost dashboard. TTFT is therefore
     unavailable for Workers AI, not zero.
   - TTFT is a provider-health signal here, not a user-facing one, because
     users receive queued results rather than a streamed response.

NOTES
========================================================================

- Backports: scrape egress validation, retry classification with jitter,
  and executor sizing fixed bugs that already existed, so they are not V2
  features in themselves. Circuit breaking, provider fallback, tenant
  fairness and spend metrics are.
- Settings lets users save their own Gemini/Tavily keys; SMTP passwords are
  encrypted, show only their last four characters, and are tested by logging
  in before save. Existing plaintext SMTP passwords upgrade on first read.
  Rotating SECRET_KEY makes saved credentials unreadable until re-entered.
- The scoring prompt asks for one evidence line per sub-component with a
  single (X/Y) at the end. Missing research fields stay null, and company
  location refers to the headquarters, not the lead's location.
- Historical numbers from the earlier Gemini configuration: the adversarial
  suite (6/6, 18 July 2026), the +/-3.5 point scoring variance used for the
  Borderline band, the run_full_eval figures, and the ~$0.03/lead cost
  calibration. Keep their dates attached; don't present them as new-run
  measurements.
